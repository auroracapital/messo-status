## What this is

An [Upptime](https://upptime.js.org) uptime monitor and status page for **Messo** (AI manager for SMB WhatsApp inboxes). It has **no build system, no dependencies, and no application code** — everything runs on GitHub Actions (cron-scheduled checks) and deploys to GitHub Pages. Published at `status.messo.cc` (see `CNAME`).

The repo is a clone of the Upptime template (`@v1.41.0`). All `.github/workflows/*.yml` files are **generated** from `.upptimerc.yml` and carry a "Do not edit this file directly" banner — they are overwritten on the weekly template sync.

## Commands

There are **no local build/lint/test/run commands** — `package.json`, Makefile, etc. do not exist. Operation is entirely via GitHub Actions, which you trigger remotely:

```bash
# Manually run a workflow (all support workflow_dispatch)
gh workflow run "Uptime CI"        # check all endpoints now
gh workflow run "Static Site CI"   # rebuild + deploy the status page to GitHub Pages
gh workflow run "Response Time CI" # record response times
gh workflow run "Graphs CI"        # regenerate response-time graphs
gh workflow run "Summary CI"       # regenerate README/summary tables

gh run list                        # see recent workflow runs
gh run watch                       # watch the latest run
```

There is no "single test" concept. To verify a config change, edit `.upptimerc.yml`, push, and let `Uptime CI` / `Static Site CI` run (or dispatch them manually).

## How to make changes

- **The only file you should hand-edit is `.upptimerc.yml`** (plus `README.md`, `CNAME`, issue templates). It is the single source of truth for monitored sites, the status-page branding/navbar, and cron schedules.
- After editing `.upptimerc.yml`, the generated workflow files update automatically on the next template sync (`update-template.yml`) — do not edit `.github/workflows/*.yml` directly; changes there are blown away.
- Adding/removing a monitored endpoint = add/remove an entry under `sites:` in `.upptimerc.yml`. Uptime CI then creates the corresponding `history/<slug>.yml`.

## Architecture / data flow

- **Uptime CI** (`uptime.yml`, every 5 min): checks each `sites:` URL, commits up/down results to `history/<slug>.yml`, opens a GitHub Issue when an endpoint is down and closes it on recovery.
- **Response Time CI** (`response-time.yml`, daily 23:00): records response times into the `history/` YAML files.
- **Graphs CI** (`graphs.yml`, daily): generates response-time graphs.
- **Static Site CI** (`site.yml`, daily 01:00): builds the Svelte/Sapper status site and deploys `site/status-page/__sapper__/export/` to GitHub Pages via `peaceiris/actions-gh-pages` (gh-pages branch).
- **Summary CI** (`summary.yml`, daily): regenerates `history/summary.json` and the status table in `README.md`.
- **Update Template** (`update-template.yml`): syncs from the upstream Upptime template, regenerating the workflow files.

The `history/` directory is the database (committed YAML/JSON, ODbL-licensed). It is machine-maintained — do not hand-edit. `assets/` holds the status-page icon.

## Conventions

- Workflows authenticate with `secrets.GH_PAT` (falling back to `github.token`). A PAT is needed for cross-workflow triggers and Pages deploys.
- Commits messages containing `[skip ci]` skip the static-site build.
- Code is MIT; the `./history` data is ODbL.
